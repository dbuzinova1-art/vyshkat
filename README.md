# ВышКат: учёт парка кикшеринга

Консольное приложение на C# (.NET 8). Транспорт принимается на баланс только после
техосмотра в сервисном центре, вещи (шлемы, док-станции, зарядные шкафы) ставятся
на баланс сразу. Приложение считает количество единиц и суммарный суточный расход
энергии, показывает транспорт для новичков (простота ≥ 6) и выводит полный инвентарь.

## Как запустить

Нужен .NET SDK 8. Все команды выполняются из корня проекта (где лежит `Vyshkat.sln`).

```bash
dotnet test                                               # 20 тестов + отчёт о покрытии
dotnet run --project src/Vyshkat                          # интерактивное меню
dotnet run --project src/Vyshkat -- data/fleet.txt        # сначала загрузить файл, потом меню
dotnet run --project src/Vyshkat < data/demo-session.txt  # демонстрация всех сценариев (bash, cmd)
```

```powershell
Get-Content data/demo-session.txt | dotnet run --project src/Vyshkat
```

## Откуда берутся данные

Данных в коде нет, всё вводится снаружи:

1. **С консоли**: пункты меню 1 и 2 спрашивают поля по одному.
2. **Из файла**: пункт меню 3 или путь в аргументах запуска. Формат: одна строка на объект,
   поля через `;`, строки с `#` и пустые пропускаются.

   ```
   scooter;KS-101;Ninebot G30;8;1.2
   ebike;EB-301;Kupers Pro;4;2.5
   bicycle;BK-201;Forward City;9
   helmet;HL-01;L
   dock;DK-02;10
   charger;CS-03;Покровка-Хаб;15
   ```

   Поля: самокат и электровелосипед — `номер;модель;простота;кВт·ч в сутки`, велосипед —
   `номер;модель;простота`, шлем — `номер;размер`, док-станция — `номер;мест`,
   зарядный шкаф — `номер;название;кВт·ч в сутки`.

   Ошибочная строка не роняет загрузку: выводится «Строка N: ошибка — …», остальные строки
   обрабатываются. В `data/fleet.txt` специально есть разряженный самокат (не пройдёт
   техосмотр), дубликат номера, неверное число полей и неизвестный вид.
3. **Сценарий через stdin**: `data/demo-session.txt` — это просто ответы на вопросы меню.
   При перенаправленном вводе приложение повторяет введённое в вывод, чтобы лог читался.
   Сценарий проходит все случаи: пустой баланс, загрузку файла с ошибками, приём и отказ на
   техосмотре, неверное число, занятый номер, все три вида вещей, неизвестный пункт меню и все отчёты.

Числа можно писать и через точку, и через запятую (`2.1` и `2,1`).

## Требование → где сделано

| Требование | Меню | Код |
|---|---|---|
| Приём транспорта после техосмотра | 1, 3 | `FleetService.RegisterTransport`, `IServiceCenter` |
| Постановка вещей на баланс | 2, 3 | `FleetService.RegisterItem` |
| Количество единиц и суточная энергия | 4 | `GetCounts`, `GetTotalDailyEnergy` |
| Транспорт для новичков (простота ≥ 6) | 5 | `Transport.IsBeginnerFriendly`, `GetBeginnerTransports` |
| Названия и инвентарные номера всего | 6 | `GetAllInventory` |

## Структура

```
src/Vyshkat/
  Domain/Interfaces.cs        IInventoriable, IPowerConsumer
  Domain/Transport.cs         Transport, KickScooter, EBike, Bicycle
  Domain/Item.cs              Item, Helmet, DockingStation, ChargingStation
  Services/IServiceCenter.cs  IServiceCenter, StrictServiceCenter, InspectionResult
  Services/IFleetRepository.cs IFleetRepository, InMemoryFleetRepository
  Services/FleetService.cs    бизнес-логика парка
  FleetFileLoader.cs          чтение файла с техникой
  InputParser.cs              разбор чисел из ввода
  ConsoleApp.cs               меню (только ввод/вывод)
  DependencyInjection.cs      регистрация сервисов в контейнере
  Program.cs                  точка входа
tests/Vyshkat.Tests/          тесты xUnit
data/                         fleet.txt и demo-session.txt
```

Слои зависят в одну сторону: `ConsoleApp` → `FleetService` → интерфейсы. `FleetService`
ничего не знает о консоли и файлах, поэтому его можно проверить без ввода-вывода.

## Логика решений

- **Две иерархии, а не одна.** `Transport` и `Item` — разные абстрактные классы: у транспорта есть
  модель, простота и техосмотр, у вещей их нет. Общее у них только то, что они стоят на балансе,
  поэтому общее вынесено в интерфейс `IInventoriable`, а не в базовый класс.
- **Энергия — отдельный интерфейс.** Потребляют энергию и транспорт (самокат, электровелосипед), и вещь
  (зарядный шкаф). Через наследование это не выразить, а через интерфейс `IPowerConsumer` — легко.
- **Техосмотр — интерфейс.** Правила приёмки меняются чаще всего, и в тестах их нужно подменять,
  поэтому `FleetService` знает только `IServiceCenter`.
- **Хранилище — интерфейс.** Сейчас данные в памяти, но `FleetService` не зависит от этого:
  файл или база данных подключатся новой реализацией `IFleetRepository`.
- **Проверка данных в конструкторах.** Объект с пустым номером или простотой 11 просто нельзя
  создать, поэтому дальше по коду эти проверки не нужны.
- **Ошибки ввода не роняют программу.** Меню и загрузчик файла ловят ошибки проверки и печатают
  понятное сообщение, а программа продолжает работу.
- **Чего сознательно нет.** Нет базы данных, отдельной стратегии для правила новичка, фабрик и
  обобщённых репозиториев: в задаче они не нужны, а за лишние абстракции снижают оценку.

## SOLID в проекте

- **S (единственная ответственность).** `FleetService` ведёт учёт, `StrictServiceCenter`
  проверяет транспорт, `InMemoryFleetRepository` хранит, `FleetFileLoader` разбирает файл,
  `ConsoleApp` общается с пользователем. Меняю формат меню — не трогаю учёт.
- **O (открытость/закрытость).** Новый вид транспорта — это новый класс-наследник
  `Transport`. `FleetService` и отчёты его подхватывают без изменений (тест
  `Extensibility_OCP_CanAddNewTransportTypeWithoutModifyingService` с моноколесом).
- **L (подстановка Лисков).** Любой `Transport` и любой `Item` работают везде, где ждут базовый
  тип: проверки корректности данных стоят в базовых конструкторах, наследники их не ослабляют.
- **I (разделение интерфейсов).** Есть два маленьких интерфейса вместо одного большого:
  `IInventoriable` (номер и название) есть у всех, `IPowerConsumer` (энергия) — только у
  самоката, электровелосипеда и зарядного шкафа. Механическому велосипеду и шлему не нужно
  притворяться, что они потребляют 0 кВт·ч.
- **D (инверсия зависимостей).** `FleetService` получает `IFleetRepository` и `IServiceCenter`
  через конструктор, а конкретные классы выбираются в одном месте — в `DependencyInjection.cs`.

## DI-контейнер

Используется `Microsoft.Extensions.DependencyInjection`. `AddVyshkat()` регистрирует
репозиторий, сервисный центр, `FleetService` и загрузчик; `AddConsoleApp(...)` регистрирует
меню с нужными потоками ввода/вывода. `Program.Main` только собирает контейнер и запускает меню.
Чтобы подменить техосмотр, достаточно зарегистрировать другую реализацию `IServiceCenter`
после `AddVyshkat()`: последняя регистрация побеждает.

## Ответы на вопросы

**1. Какой принцип SOLID выражен ярче всего?**
Разделение интерфейсов (I). Энергия считается как `OfType<IPowerConsumer>()` по всему
балансу, поэтому в отчёт попадают ровно те объекты, которые реально потребляют энергию, — и
транспорт, и зарядный шкаф, без проверок конкретных типов. Это проверяет
`TotalDailyEnergy_OnlySumsPowerConsumers_ISP`.

**2. Какой принцип сознательно ограничен?**
Открытость/закрытость (O) для правила новичка: порог `SimplicityScore >= 6` записан прямо в
`Transport.IsBeginnerFriendly()`. Можно было сделать отдельную стратегию `IBeginnerPolicy`, но
правило одно и в задании не меняется, так что лишняя абстракция была бы переусложнением. Если
появятся разные правила (например, для разных районов), вынесу их в интерфейс.

**3. Что придётся менять при добавлении…**
- *нового вида транспорта* — только новый класс-наследник `Transport` (и `IPowerConsumer`, если он
  электрический). Чтобы его можно было вводить с консоли и из файла, добавляется пункт в
  `ConsoleApp` и ветка в `FleetFileLoader.ParseLine`. Учёт и отчёты не меняются.
- *нового сотрудника* — по ТЗ сотрудники на баланс не ставятся, поэтому класс `Employee` **не**
  реализует `IInventoriable` и не попадает в инвентарь; для него нужны своё хранилище и сервис,
  существующий код не меняется. Если сотрудник (механик) должен проводить техосмотр, это новая
  реализация `IServiceCenter` и одна строка регистрации в контейнере.
- *склада запчастей* — новый интерфейс хранилища (например, `ISparePartsRepository`) и свой
  сервис рядом с `FleetService`. Существующие классы не меняются; если запчасти должны попадать
  в общий инвентарь, они реализуют `IInventoriable`.

**4. Какой тест фиксирует правила техосмотра и новичка и как подменяется зависимость?**
- `RegisterTransport_WhenServiceCenterRejects_DoesNotAddToFleet` и
  `RegisterTransport_WhenServiceCenterAccepts_AddsToFleet`: в `FleetService` через конструктор
  передаются фейки `AlwaysRejectServiceCenter` / `AlwaysAcceptServiceCenter` (`Fakes.cs`).
- `ServiceCenter_IsReplacedInContainer`: та же подмена, но через DI-контейнер —
  `.AddVyshkat().AddSingleton<IServiceCenter, AlwaysRejectServiceCenter>()`.
- `StrictServiceCenter_RejectsDischargedAndApprovesWorking` проверяет настоящий сервисный центр.
- `BeginnerRule_ChecksBoundaryConditions` (Theory: 1, 5, 6, 10) фиксирует границу «≥ 6».

**5. Что сделал ИИ, а что я сама?**

ИИ использовался как помощник: для ревью кода, поиска ошибок и части реализации.

*Сделала сама:*
- доменную модель: интерфейсы `IInventoriable` и `IPowerConsumer` (энергия вынесена отдельно, чтобы
  механический велосипед и шлем не возвращали фиктивный 0), иерархии `Transport` и `Item`, правило
  `IsBeginnerFriendly`;
- сервисный слой: `IServiceCenter` + `StrictServiceCenter`, `IFleetRepository` + `InMemoryFleetRepository`
  с проверкой уникальности номеров, `FleetService`;
- первые тесты: фейки `AlwaysAcceptServiceCenter` / `AlwaysRejectServiceCenter`, граничные значения
  правила новичка, тест расширения с моноколесом.

*Сделал ИИ после ревью моего варианта:*
- нашёл ошибки: бесконечный цикл меню при конце ввода, демо-данные, записанные прямо в код
  (противоречит уточнению к заданию), не до конца покрытие тестами;
- в итоговой версии SimpleContainer нет: его заменил стандартный контейнер, потому что тот сам подставляет зависимости по конструкторам
- вынес меню в `ConsoleApp`, написал несколько комментариев для логики кода и сценарий `demo-session.txt`;
- дописал тесты;
- подготовил черновик README: структуру разделов, таблицы;
- генерация стандартных шаблонов Arrange-Act-Assert для xUnit, тестов разбора пользовательского ввода и проверки сценария автоматической демонстрации (`data/demo-session.txt`);

*Что проверила и переработала я:*
- FleetService.RegisterTransport возвращал одно и то же дважды. Было (bool Success, InspectionResult Result), хотя Success всегда совпадал с Result.IsApproved. Теперь метод возвращает просто InspectionResult
- Вместо тернарного оператора и отдельного метода CreateElectric сделала обычный switch по типу, такой же, как для вещей. Я считаю, так проще читать.
- скорректировала таргеты в файлах `.csproj` и параметры тестового раннера, устранив конфликты версий SDK и обеспечив стабильное прохождение тестов с реальным покрытием.

## Ограничения

- Данные хранятся в памяти и пропадают после выхода (так задумано для этой задачи; хранилище
  спрятано за `IFleetRepository` и заменяется без правки сервиса).
- Техосмотр проверяет только заряд аккумулятора электротранспорта.
